# Ownership Map — Tauka Shared Database
> **Canonical location.** This is the root-level unified ownership file for all three projects.
> Each project-level `shared-db/OWNERS.md` must mirror this file.
> Last updated by: tauka-python on 2026-08-28 (§85/§86 — the cohort_matching domain, and tauka-python registered as a shared writer of the cohort tables)

---

## Ownership Rules

1. Only the owning project may `CREATE TABLE` or `ALTER TABLE` in its domain.
2. Other projects get READ access — query only, never DDL.
3. Shared-write tables are explicitly marked — all others are write-owner-only.
4. If you need a column on a table you don't own, add to `shared-db/CONFLICT_LOG.md` as a `SCHEMA_REQUEST`.
5. If two projects both claim ownership of the same table, that is a CONFLICT — log it.
6. The `app` schema is used for all tables. `public` schema is not used.
   *One documented exception:* `web.interest` (tauka-react-web) — see below.
7. tauka-python uses `supabase.schema("app").table(...)` for all table access.
8. tauka-flutter uses Supabase Dart SDK with `.schema('app')` qualifier.
9. tauka-react-web uses `supabase.from('table')` with the supabase-js client initialized to the `app` schema.

## The `web` schema — the one documented exception to Rule 6

`web.interest` is the sole table outside `app`. It is **marketing-site signup
capture** (`email`, `country`, `phone`, `languages[]`, `category`,
`pioneer_number`), written by the public landing page before a user account
exists — so it is deliberately outside the authenticated `app` surface.

- **Owner: tauka-react-web.** Only that project may `CREATE`/`ALTER` it.
- **No API role has USAGE on the `web` schema** (`anon`, `authenticated`, and
  `service_role` all lack it), so the table is not reachable over PostgREST
  despite carrying table-level grants. Those grants are vestigial.
- **RLS is enabled** with a single `INSERT` policy (`"public Insert"`).
  The former `"Enable read access for all users"` SELECT policy was dropped in
  §52 — it was `USING (true)` to PUBLIC and would have exposed every signup's
  email and phone the moment anyone granted schema USAGE.
- Ownership was assigned 2026-08-09 (CONFLICT-016). tauka-flutter applied the
  §52 security fix before ownership existed; any further change belongs to
  tauka-react-web.
- Do **not** treat this as precedent. Rule 6 stands: new tables go in `app`.

## RLS Read Scope — tables where "who can read" is not "everyone authenticated"

Ownership answers *who may write*. The tables below additionally restrict
*who may read which rows*, which is easy to miss because the owner is
unchanged and no column moved.

**A policy on this list can be wrong in the widening direction and look fine.**
`voice_recordings_select_own_or_tutor_admin` read `app.is_tutor()` — a predicate
that takes no subject and therefore answers "is the caller *a* tutor", not "is
this *their* student". It sat in production, in the heaviest data category the
platform holds, until Phase 6 read it while scoping a feature (CONFLICT-041).
When adding a row here, name the predicate **and its argument**: a rule with no
subject is not a read scope.

| Table | Rows a caller can read | Enforced by | Added |
|---|---|---|---|
| `app.broadcast` | All `program` / `level` / `cohort` posts; `course` posts only if enrolled in or teaching that course, or its author, or admin | `broadcast_select_audience` → `app.is_enrolled_in_course()` | §55, 2026-08-14 |
| `app.user_profiles` | Own row; assigned students if tutor; all if admin; **anyone sharing a conversation with the caller** | `user_profiles_select_conversation_peer` → `app.shares_conversation_with()` | §56, 2026-08-14 |
| `app.voice_recordings` | Own rows; the caller's students on a paid tier; admins | `voice_recordings_select_own_or_teacher_admin` → `app.can_read_activity()` | §79, 2026-08-28 — **narrowed**, see CONFLICT-041 |
| `app.tutor_standing` | Own rows; admins | `tutor_standing_select_own` | §79, 2026-08-28 |
| `app.tutor_feedback` | Own submissions (including the admin's reply); admins | `tutor_feedback_select_own` | §79, 2026-08-28 |
| `app.exercise_assignment` | Rows naming the caller as student **or** as the assigning tutor | `exercise_assignment_select_student` / `_select_tutor` | §79, 2026-08-28 |

Consequences worth knowing before debugging either table:

- A query that returns fewer rows than the table contains is probably correct,
  not broken. Verify by impersonating a user rather than reading as service
  role, which bypasses RLS entirely:

  ```sql
  BEGIN;
  SET LOCAL role authenticated;
  SET LOCAL request.jwt.claims = '{"sub":"<user-uuid>","role":"authenticated"}';
  SELECT ...;
  ROLLBACK;
  ```

- `program` / `level` / `cohort` broadcasts are still visible to **every**
  authenticated user. Only `course` is scoped. Their targeting columns remain
  decorative — narrowing them is a separate, deliberate decision.
