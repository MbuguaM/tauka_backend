# Architecture Index — Tauka Shared Database
> **Canonical location.** This file is the root-level unified index for all three projects.
> Project-level copies (`tauka/shared-db/`, `tauka_py_backend/shared-db/`, `tauka-react-web/shared-db/`) must be kept in sync with this file.
> Last updated by: tauka-python on 2026-08-28 (§85/§86 — new domain: cohort_matching)

---

## How to Use This File

1. Look up the domain or table you need in the maps below.
2. Note the **Owner Project** and **Domain File**.
3. Read `tauka/shared-db/domains/[domain].md` for full rationale, column details, extension rules, and anti-patterns.
4. Read `tauka/shared-db/schema/db.sql` for exact DDL before writing any query or migration.
5. Check `shared-db/OWNERS.md` to confirm your project's write permissions.
6. Check `shared-db/CONFLICT_LOG.md` before creating any new table.

## Global Anti-Patterns

> These rules apply across ALL projects. Never remove entries; only append.

- **Never store money as a float.** Monetary amounts are **integer minor units**. Older single-currency tables use `amount_cents`; anything spanning currencies uses `*_minor` **plus an explicit `currency` (ISO 4217, NOT NULL)** — §75 onwards, because D-17 settled a rate card per country and "cents" is simply wrong for a Ugandan shilling. `numeric` is acceptable only for an FX **rate**, never for an amount.
- **A money balance is never a column.** `app.float_ledger` and `app.session_entitlement` are append-only and a balance is a fold over them. Where a running total is stored alongside (`float_ledger.balance_after_minor`) it is a **cross-check for reconciliation**, not the source of truth, and it is written by one function under a lock.
- **Never fold a balance across currencies.** Partition by currency or forbid mixed rows (§11.3).
- **Scanning message content is a different consent question from telemetry** (L-008). The shipped design warns the sender at compose time on their own device and stores only an anonymous per-class counter. **Never add a user id, conversation id, message id or matched text to `app.trust_warning_stat`**, and never scan stored messages, without reopening L-008 first.
- **`app.unit.unit_order` is NOT unique.** Production carries preliminary units (`introduction`, `alphabet`) at orders 1 and 2, colliding with content units 1 and 2. Any computation over `unit_order` — a phase band, a milestone target, a "how far through" number — **must filter `is_preliminary = false`** or it counts the first units twice. `app.unit` has no phase or level column at all, which is why `unit_order` is the axis in the first place (`commitment_service.parse_milestone`, `curriculum.phases`).
- **A reschedule is not a cancel plus a book.** Composed from those two, a move made outside the cancellation window silently costs the student the session — cancel does not refund there and book consumes again. `app.reschedule_one_to_one()` moves the row in one transaction and writes **nothing** to `app.session_entitlement`: a refund/consume pair would net to zero and still be wrong, because the ledger is the record of what was granted and spent, and a move is neither.
- **A read-scope predicate must take a subject.** `app.is_tutor()` answers "is the caller a tutor" and has no argument; `app.teaches_student(uuid)` and `app.can_read_activity(uuid)` answer "is this *their* student". A SELECT policy built on the first is not scoped to anything, reads as intentional, and widens silently — `voice_recordings` carried exactly that for months (CONFLICT-041). **Never use a subjectless predicate as the only branch of a row-level read rule.**
- **"Sessions delivered" means `cohort_session.lead_tutor_id` + `one_to_one_session.tutor_id`.** `app.tutor_sessions` was never applied to production and `tutor_payroll`/`payroll_line_item`/`tutor_rates` were dropped (CONFLICT-040). Anything counting delivery — pay, standing, a dashboard — reads those two columns through `payout_service.delivered_sessions`, so the definition has exactly one home. A second copy will eventually promote a tutor the payout run did not pay.
- **Delivery is never inferred from a timestamp.** A past session nobody marked is *not marked yet*, never *delivered* and never *missed*. `app.mark_attendance` and `app.mark_one_to_one_outcome` are tutor-written for the same reason: `payout_service` pays for `completed` rows, so a sweep that auto-completed past sessions would pay for lessons nobody attended.
- **Never add a fifth `tier` value for a product.** `app.student.tier` is the entitlement axis — what a user can *use*. A commitment, a plan or a promise is a separate row that NAMES a tier (`app.enrollment_commitment.tier`, §76). Collapsing the two puts "what you can use" and "what you promised" in one column and breaks every gate that switches on it.
- Never create a generic key-value metadata table — use specific columns or a typed `jsonb` column instead.
- All timestamps are UTC, stored as `TIMESTAMPTZ` (PostgreSQL `timestamp with time zone`).
- Soft deletes use a `deleted_at TIMESTAMPTZ NULL` column. Never use a boolean `is_deleted` flag.
- All tables live in the `app` schema, never `public`. Access the schema explicitly: `app.<table>`.
- Never store sensitive credentials (Stripe keys, API tokens) in a DB column accessible by RLS-authenticated users. Use Supabase Vault or environment variables and expose only masked display values.
- Enum columns use `TEXT + CHECK` constraints, not PostgreSQL `ENUM` types. This allows `ALTER TABLE` without type migration.
- User identity is always `auth.uid()` from Supabase Auth — never trust a `user_id` supplied by the client without an RLS `USING (user_id = auth.uid())` guard.
- Never create `dictionary_entry` or `word_pair` tables — entries are stored inline as JSON arrays in `app.dictionary.dict` and `app.anki_deck.deck` (see course_content domain). **`app.dictionary_entry` existed in production anyway** from an applied `Proposed_additions_db.sql`, empty and unread, and was **DROPPED 2026-08-28 (§81.3)**; CONFLICT-038 closed.
- Never create `exercise_sessions` — the canonical exercise result table is `app.exercise_result` (singular).
- **`app.student.tutor_id` no longer exists (§73).** A student has one *home* tutor and a *guest pool* with different rights and lifetimes; that is `app.student_tutor_link`. Never re-add a single-tutor column to `app.student`, and never define "my student" as a direct id comparison — the canonical definition is `app.teaches_student()`, the course join (CONFLICT-033).
- **A session balance is never a counter.** `app.session_entitlement` is append-only and a balance is `SUM(...)` over it. A mutable counter that drifts by one costs a customer a session they paid for, with no record to reconstruct it from. The append-only rule is enforced by a trigger, which fires for the service role too.
- `subscription_tier` canonical values are: `free | learner | tutor | intensive`. Never use `tutor_tier`.
- The `app.user_profiles.subscription_tier` column is a denormalized cache kept in sync by `trg_sync_student_tier`. Never update it directly from any project — it is written by the trigger when `app.student.tier` changes.
- The Python backend (tauka-python) is the sole authority on `app.student.tier`, `stripe_customer_id`, and `stripe_subscription_id`. No other project may write these columns.
- The test/referral share flow supports exactly two channels: `whatsapp` and `copy_link`. The `email` channel was removed. `test_referrals.recipient_email` is kept in schema but no longer written.
- OTP email verification is used at the **mid-test email gate only** (purpose `'test_gate'`). The `email_verifications` table purpose column accepts only `'test_gate'`.
- **Course broadcast channels have no membership table (§55).** Enrolment in
  `app.student_course` IS the subscription: `broadcast.target_type = 'course'`
  posts are scoped by RLS via `app.is_enrolled_in_course()`. Never add a
  channel-subscription table — a second source of truth would drift from
  enrolment and misdeliver.
- **Realtime requires publication membership.** Postgres Changes are delivered
  only for tables in the `supabase_realtime` publication. A subscription to a
  non-member table reports `SUBSCRIBED` and then never fires, with no error.
  Only `app.messages` and `app.broadcast` are members (added §55); every other
  documented subscription is inert. See CONFLICT-019.
- **`user_profiles` is not a user directory.** Every SELECT policy is an
  existence check scoped to a relationship the caller is already in: own row,
  admin, assigned tutor, or conversation peer (§56). Do not add a policy that
  returns rows for users the caller has no relationship with.
- **`user_profiles` cannot be PostgREST-embedded from `messages` or
  `conversation_participants`.** Both reference `auth.users(id)`, not
  `app.user_profiles(id)`, so there is no FK to traverse and the whole query
  fails with PGRST200. Fetch display names in a separate batched lookup.

## SECURITY DEFINER Helper Functions

RLS policies cannot read another RLS-protected table directly — the subquery is
filtered by *that* table's policies and silently returns false (or recurses,
42P17). Every cross-table predicate therefore goes through a
`STABLE SECURITY DEFINER` function with `search_path` pinned to `app`.

| Function | Answers | Reads | Used by |
|---|---|---|---|
| `app.is_admin()` | Is the caller an admin? | `admin_users` | Admin policies across every domain |
| `app.is_tutor()` | Is the caller a tutor? | `tutor` | `broadcast` INSERT, tutor-only policies |
| `app.is_conversation_participant(uuid)` | Is the caller in this conversation? | `conversation_participants` | `conversations`, `conversation_participants` SELECT |
| `app.is_enrolled_in_course(uuid)` §55 | Is the caller enrolled in / teaching this course? | `student_course`, `tutor_course` | `broadcast_select_audience` (course channels) |
| `app.shares_conversation_with(uuid)` §56 | Does the caller share a conversation with this user? | `conversation_participants` | `user_profiles_select_conversation_peer` |
| `app.teaches_student(uuid)` §73.2 | Is this the caller's student? **The canonical answer** (D-05) | `tutor_assignment`, `student_course` | `exercise_result`, `progress_snapshots`, `exercise_assignment` INSERT |
| `app.can_read_activity(uuid)` | Same course join, **plus a paid tier** | `tutor_assignment`, `student_course`, `student` | `activity_file`/`activity_summary`, `speech_submission`, `voice_recordings` (§79) |

### Booking RPCs (SECURITY DEFINER, not RLS predicates)

| Function | Does | Touches `session_entitlement`? |
|---|---|---|
| `app.book_one_to_one(...)` | Books a slot | **Yes** — one `consume` |
| `app.cancel_one_to_one(...)` | Cancels | **Yes** — one `refund`, unless inside the window or `refund_forfeited` |
| `app.reschedule_one_to_one(...)` §80 | Moves a booking | **No, deliberately.** Stamps `refund_forfeited` when moved from inside the window |

Adding a policy that needs data from another table? Add a function here rather
than inlining the subquery.

**And check the function takes the subject you mean.** `app.is_admin()` and
`app.is_tutor()` are *role* checks with no argument — correct for an admin
branch, wrong as the only branch of a per-row read rule. The two subject-taking
predicates are `app.teaches_student(uuid)` (the canonical "my student") and
`app.can_read_activity(uuid)` (the same join plus a tier gate). Picking the
role check by mistake produces a policy that looks deliberate and is not
scoped — see CONFLICT-041.
