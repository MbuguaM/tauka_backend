## How to Use This File

When you discover a duplicate table, mismatched column type, missing table, broken FK, or any cross-project schema issue:
1. Log it here with a new sequential conflict number.
2. Add a comment in your code: `// CONFLICT: see CONFLICT_LOG.md #[number]` (or `# CONFLICT: ...` in Python).
3. Use a workaround and document it.
4. Inform the developer — do NOT silently fix conflicts.

### CONFLICT-014: app.user_profiles UPDATE policy recurses (42P17) — every owner write fails
- **Detected by:** tauka-flutter
- **Date:** 2026-08-19
- **Type:** BROKEN_POLICY
- **Status:** RESOLVED 2026-08-19 — §58 applied to production (migration `fix_user_profiles_policy_recursion`). Verified: the recursive policy is gone and `trg_guard_user_profile_privileges` is in place.
- **Details:** The §48 policy `"users update own profile"` enforces the no-self-promotion
  rule with a `WITH CHECK` that selects from `app.user_profiles` — the table it guards:
  ```sql
  WITH CHECK (
    user_type = (SELECT user_type FROM app.user_profiles WHERE id = auth.uid())
    AND subscription_tier = (SELECT subscription_tier FROM app.user_profiles WHERE id = auth.uid())
  )
  ```
  Evaluating it re-enters the policy, so **every** owner UPDATE fails with
  `infinite recursion detected in policy for relation "user_profiles" (42P17)`.
  `app.is_admin()` and `app.shares_conversation_with()` are both SECURITY DEFINER and are
  NOT implicated.
- **Blast radius:** onboarding never persists. Production shows `user_type` and
  `completed_at` null for 3 of 5 `auth.users`. Because `AuthStateManager` resolves the
  app-wide role from `user_profiles.user_type`, every tutor reads back as a student, and
  a user who completes onboarding is walked through it again on the next device.
- **Resolution (§58):** a policy cannot see `OLD`, which is why the original reached for
  a subquery. Move the rule to a `BEFORE UPDATE` trigger, which can, and drop the policy.
  The trigger clamps the two protected columns rather than raising, so a self-promotion
  attempt is a no-op on those columns while the legitimate part of the write still lands.
  It exempts `auth.uid() IS NULL` (service role, and `trg_sync_student_tier` writing
  `subscription_tier` from `app.student.tier`) and admins, and permits `user_type`
  NULL → value once, which is onboarding choosing a role.
- **Apply:** run §58, then re-open the app; `OnboardingData._flushPendingRemote` rewrites
  the missing fields on next launch.

### CONFLICT-013: self-selected tutors get no dictionary access
- **Detected by:** tauka-flutter
- **Date:** 2026-08-19
- **Type:** IMPLICIT_CONTRACT
- **Status:** RESOLVED 2026-08-20 — **`tutor_course` confers dictionary read access.**
  Migration `dictionary_select_include_tutor_course` applied to production and
  verified: the policy now carries three arms (`student_course`,
  `tutor_assignment`, `tutor_course`) plus the admin escape.
- **Resolution:** reading 2 was chosen — a tutor who self-selects a course to
  teach SHOULD read that course's dictionaries. `dictionary_select_enrolled_or_tutor`
  gained a third arm mirroring the two beside it. `tutor_course` has no
  `deleted_at`, so unlike the `tutor_assignment` arm there is nothing to filter.
  No SECURITY DEFINER helper was needed: `tutor_course` carries
  `tutor_course_select_all USING (true)`, so the subquery is not filtered out
  from under the policy — had it been owner-scoped instead, the new arm would
  have matched nothing and the fix would have appeared to do nothing at all.
  `tutor_course`'s policies do not reference `app.dictionary`, so there is no
  cycle to recurse on (cf. CONFLICT-014).
- **Widened access, stated plainly:** anyone with a row in `app.tutor_course`
  for a course can now read that course's dictionaries. That table is
  self-service — `tutor_course_insert_own` lets a user insert their own row —
  so this is a deliberate decision that self-selection is sufficient proof of
  intent to teach. Admin assignment via `tutor_assignment` remains the stronger
  signal and is unchanged.
- **Details:** `app.dictionary`'s SELECT policy, `dictionary_select_enrolled_or_tutor`, grants
  access to students via `app.student_course` and to tutors via **`app.tutor_assignment`**
  (admin-managed). It does not consider `app.tutor_course`, which is what the Flutter course
  picker writes when a tutor selects a course to teach. A tutor who self-selects a course is
  therefore in `tutor_course` but not `tutor_assignment`, and reads zero dictionary rows for a
  course that has three. Observed live: `DictionaryDownload ... RETURNING (0 dictionaries)` and
  `prefetch verify incomplete — missing: [dictionary.json]`.
- **Students are NOT affected** — the `student_course` arm of the policy works correctly.
- **The open question is which table means "this tutor teaches this course".** Two readings, and
  they are not equivalent:
  1. `tutor_assignment` is the authority and self-selection via `tutor_course` is only a
     preference. Then the policy is correct and the course picker is promising tutors something
     it cannot grant — the UI should say so.
  2. `tutor_course` should also confer read access. Then the policy needs a third arm. This
     widens who can read course content, so it is a security-relevant change and needs sign-off.
- **Current workaround:** none needed for the freeze — `isCourseReady`/`isDownloadReady` are
  unconditional for tutors as of 2026-08-19, so the missing dictionary no longer blocks
  navigation. The tutor simply has no dictionary data.


### CONFLICT-022: the entire classic-chat read path was broken by four stacked faults
- **Detected by:** tauka-flutter (device testing)
- **Date:** 2026-08-14
- **Type:** QUERY_SHAPE / MISSING_RELATIONSHIP
- **Status:** RESOLVED (2026-08-14)
- **Details:** `chat_messaging.md` documented classic chat as "LARGELY COMPLETE",
  but no user could see a conversation or a message. Four independent faults,
  each hidden by the one before it, and every one of them silently swallowed:

  1. `getUserConversations` embedded `messages!inner(...)`. An INNER join drops
     any conversation with **zero messages**, so a newly created conversation
     was invisible — and could not receive a first message, because it never
     appeared to open. Broke every new DM and every language-exchange match at
     the moment of creation.
  2. The same query is rooted at `conversation_participants`, but the result
     rows were passed straight to `Conversation.fromJson`, which reads `id` and
     `type` off a **conversations** row. `json['type'] as String` was a null
     cast → `TypeError`, discarded by a bare `catch` in
     `Chatstate._loadChatItems`. Chat list permanently empty, no error anywhere.
  3. The embedded projections were narrower than the nested models' non-null
     casts: `Message.fromJson` requires `conversation_id`,
     `ConversationParticipant.fromJson` requires `id` + `conversation_id`.
     Same "Null is not a subtype of String" failure one level down.
  4. **No render path existed for real conversations.** The chat list was wired
     only to `Chatstate.directMessageSeeds`, which returns `[]` when real
     conversations exist and `kSeedDirectMessages` (itself `const []`)
     otherwise — empty in both branches. Fixing 1–3 therefore changed nothing
     visible.

  Separately, `getMessages` embedded
  `user_profiles!messages_sender_id_fkey(*)`. `messages.sender_id` references
  **`auth.users(id)`**, not `app.user_profiles(id)`, so PostgREST has no
  relationship to traverse and rejected the **entire** query with `PGRST200` —
  swallowed by another bare `catch` in `loadMessages`, leaving every thread
  blank even once the conversation opened.
- **Resolution:** left join + unwrap to conversation rows + widened
  projections + a real `Chatstate.directMessages` getter; sender embed removed
  and display names resolved via a batched `getUserProfilesByIds()` lookup
  (enabled by §56). Both silent `catch` blocks now log with a stack trace in
  debug. Verified on-device: conversation list, thread, and live Realtime
  delivery all confirmed working.
- **Lesson:** every fault here was invisible because an exception was
  discarded. A `catch` that exists to keep cached data on screen must still
  log — a silent `catch` around a parse turns a crash into a permanently empty
  screen with no diagnostic.

### CONFLICT-018: the `user_profiles` self-promotion guard is inert — two permissive UPDATE policies OR together
- **Detected by:** tauka-flutter
- **Date:** 2026-08-12
- **Type:** RLS_BYPASS (security)
- **Status:** OPEN — **needs a human decision before any policy change**
- **Details:** `app.user_profiles` carries **two** permissive UPDATE policies for the
  `authenticated` role:

  | Policy | USING | WITH CHECK |
  |---|---|---|
  | `users update own profile` | `auth.uid() = id` | `user_type` unchanged **AND** `subscription_tier` unchanged |
  | `user_profiles_update_own` | `auth.uid() = id AND deleted_at IS NULL` | `auth.uid() = id` |

  PostgreSQL combines permissive policies for the same command with **OR**. The second
  policy's `WITH CHECK (auth.uid() = id)` is true for a user's own row, so the whole check
  passes regardless of what the first policy says. The guard it was written to provide —
  §48, "the Flutter client never modifies `user_type` directly" — does not hold.

  Consequence: any authenticated user can `UPDATE app.user_profiles SET subscription_tier
  = 'intensive', user_type = 'tutor' WHERE id = auth.uid()`. `TierGatingService` reads
  `user_profiles.subscription_tier` for feature gating, so this is a client-side paid-tier
  bypass, and `user_type` drives which UI (student vs tutor) is rendered.

  Verified against production on 2026-08-12 by reading `pg_policies`, not inferred from docs.
- **Contradicts the docs:** `tauka/shared-db/domains/identity_access.md` §2 "Key invariants"
  states `user_type` is "never modified by the Flutter client directly (§48 RLS policy
  blocks self-promotion)" and that `role` may only be written by service_role. Neither is
  currently true; there is also **no `role` column** on the table in production.
- **Why it is not fixed here:** tightening this changes authentication behaviour for every
  existing client. Note that the Flutter onboarding write *relies* on the permissive
  outcome today — `OnboardingData._toMap()` sends `user_type` on every step, and tightening
  the policy without changing that code would break onboarding for every new sign-up.
  The two must move together.
- **Suggested resolution (needs approval):** drop `user_profiles_update_own`, keep the
  guarded policy, and add `deleted_at IS NULL` to its `USING`. Then either stop sending
  `user_type` from `_toMap()` after the first write, or add a narrow policy permitting
  `user_type` to be set exactly once while it is NULL.

### CONFLICT-017: `app.dictionary.dict` is an authoring SAMPLE, not the shipped dictionary
- **Detected by:** tauka-flutter
- **Date:** 2026-08-09
- **Type:** IMPLICIT_CONTRACT
- **Status:** OPEN (accepted by design — documented, not a bug to "fix" in the DB)
- **Details:** the `dict` column and the file at `dict_url` are **not** two copies of
  the same thing, which the column name strongly implies. Measured against
  production on 2026-08-09:

  | Dictionary | `dict` entries | `dict_url` file entries | entries with audio in `dict` |
  |---|---|---|---|
  | amharicAdjectives | 138 | 138 | 0 |
  | amharicVerbs | 143 | 143 | 0 |
  | amharic_enhanced | **20** | **3,080** | 0 (nested sample only) |

  `dict` is 3.5–5.2 kB per row. The published files are 0.15–3.11 MB, and they are
  the only place the content-addressed `audio_url` / `audio_url_male` /
  `audio_url_female` filenames exist. **A client that caches the row without
  resolving `dict_url` loses 2,942 words and all pronunciation.**
- **Why this is dangerous rather than merely surprising:** the cache-invalidation
  version (§51) is `SUM(app.dictionary.version)`, a property of the ROW. A cache
  built from the row alone therefore carries the *correct* version, so
  `ContentVersionChecker` reads it as current forever and nothing ever repairs it.
  Wrong content that looks fresh is worse than missing content.
- **How it shipped:** `Dictionarystate._loadDictItems` wrote
  `getDictionaryByCourse()` rows straight to
  `courses/<id>/dictionary.json`, while the three copies in `CourseState`
  resolved `dict_url` correctly. The broken writer ran on every online visit to
  the dictionary page, so it overwrote the good cache. Symptom: the pronunciation
  play buttons rendered as empty boxes and the voice toggle disappeared.
- **This project assumes:** the file at `dict_url` is authoritative whenever
  `dict_url` is non-null; `dict` is only a fallback for rows that have no
  `dict_url`. All caching goes through
  `lib/src/services/dictionaryDownloadService.dart` — do not add a fourth writer.
- **Resolution needed:** none in the DB. If `dict` is ever intended to be
  authoritative again, it must be repopulated for **all** rows first, and the
  audio filenames must be included, or this regresses silently.
- **See also:** CONFLICT-014 (`dict_url` missing from the canonical schema).
