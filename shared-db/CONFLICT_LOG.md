## How to Use This File

When you discover a duplicate table, mismatched column type, missing table, broken FK, or any cross-project schema issue:
1. Log it here with a new sequential conflict number.
2. Add a comment in your code: `// CONFLICT: see CONFLICT_LOG.md #[number]` (or `# CONFLICT: ...` in Python).
3. Use a workaround and document it.
4. Inform the developer — do NOT silently fix conflicts.

### CONFLICT-048: tauka-python writes two tables whose docs said "tauka-flutter only" — REGISTERED, not resolved by fixing

**Filed 2026-08-28 by tauka-python (migration §86, backlog O-16).**
**Status: REGISTERED. This is the intended design, logged so it is not later
found and "corrected".**

`tutor-cohort-matching-plan.md` §7 puts the cohort matcher in tauka-python.
§5.0 of the same plan settled that **tauka-flutter owns the cohort domain and
its DDL** — four canonical documents said so and one dissented, and the database
settled it: every write policy on all four cohort tables is `app.is_admin()`,
an *authenticated user* predicate, not a service-role bypass. They were built
for an admin using the Flutter admin dashboard.

**But the matcher is the thing that forms cohorts.** So as of §86,
**tauka-python INSERTs `app.cohorts` and `app.cohort_memberships`** through the
service role. That is exactly the `app.student.tier` pattern — DDL owned by one
project, one specific write path owned by another — and §5.0 required it be
"an explicit shared-write entry in `OWNERS.md` naming the columns and the
writer, rather than tauka-python quietly writing a table whose docs say
'tauka-flutter only'". This entry and the two rows in OWNERS.md are that.

**The columns, exhaustively:**

| Table | tauka-python writes | tauka-python must NEVER write |
|---|---|---|
| `app.cohorts` | INSERT at formation; UPDATE of `status`, `band_lesson_low`, `band_lesson_high`, `intake_cycle` | `health_score` / `health_status` / `health_computed_at` — the `cohort-health` function's (§84); `tutor_id` after formation — a tutor change is a §1.7 **handoff**, not a rematch; `recording_consent` — the members' answer, not the platform's |
| `app.cohort_memberships` | INSERT on offer acceptance; UPDATE of `status`, `left_at`, `removal_reason` | everything else |

**No RLS policy was added, and none should be.** The write policies are
`app.is_admin()`; the service role bypasses RLS entirely. A policy naming
tauka-python would widen the **authenticated** surface to grant something the
service role already has — which is precisely how a shared-write path becomes a
client-write path by accident.

**A cohort is created with zero members.** Membership is what *accepting an
offer* creates (`offer_service.accept`). If a future change writes memberships
at formation it will have placed people who were never asked, and the difference
between an offer and an assignment will have been lost in a refactor.

**Related, and deliberately NOT done:** `app.match_offer` has no client write
policy at all. See `tauka/shared-db/domains/cohort_matching.md` §2.

### CONFLICT-047: language exchange has TWO tables, and the client and the matcher use different ones
- **Detected by:** tauka-flutter (plan O-20, repairing `match-exchange-partner`)
- **Date:** 2026-08-28
- **Type:** DUPLICATE_OBJECT + CROSS_PROJECT_MISMATCH
- **Status:** **OPEN — and it blocks the repair of `match-exchange-partner`.**

**Both tables exist in production. Both hold 0 rows. They model the same thing.**

| Table | Domain | Shape | Who uses it |
|---|---|---|---|
| `app.langexchange` | social_media | `id, lang_a, lang_b, user_a, user_b, deleted_at` | **tauka-flutter** — four queries plus an RPC in `supabaseService.dart:2443–2546` |
| `app.language_exchange_match` | broadcast | `id, user_a_id, user_b_id, conversation_id, matched_at, rematch_available_at, status, ended_at, ended_by` | **the `match-exchange-partner` Edge Function**, and a Dart model at `shared_db.dart:1453` that nothing calls |

**So the app writes and reads one table while the matcher writes the other.**
Deploying `match-exchange-partner` as written would produce matches the app
cannot see, in a table nothing reads, and neither side would error — the failure
would look like "the matcher found nobody".

**This compounds CONFLICT-021, which is still open from 2026-08-14.**
`language_exchange_match.conversation_id` is supposed to point at a real
`app.conversations` row, but `conversations_type_check` rejects `'exchange'`,
which is the type the client sends. So even the richer of the two tables cannot
be populated end to end.

**And the repair's own premise was wrong.** `match-exchange-partner` selects five
`user_profiles` columns that do not exist. Three of them should never be added
there:

| Column the function wants | Where that data already belongs |
|---|---|
| `native_language`, `target_language` | `app.user_languages`, whose `type` is already `'known'` \| `'target'` with an `is_primary` flag — exactly this shape |
| `cohort_id` | `app.cohort_memberships (cohort_id, user_id, status)` — the source of truth. A column here would be a second one, and they would drift |
| `timezone_offset`, `is_exchange_visible` | **genuinely absent.** These two are the only real additions |

Adding all five would give a user's languages a **fourth** representation —
after `user_profiles.known_languages` (jsonb, 1 row), `app.user_languages`
(normalised, 0 rows, referenced by no Dart code) and `app.langexchange`'s
`lang_a`/`lang_b`.

**Why this is not being fixed here.** Every option is a product decision:

- **Which table wins.** `langexchange` has the working client code;
  `language_exchange_match` has the lifecycle columns (`status`,
  `rematch_available_at`, `ended_by`) that §2.6's rematch rules need. Keeping
  both is the only option that is definitely wrong.
- **Whether `user_languages` gets adopted or dropped.** `language_registry.md`
  already says it is unused and "safe to drop if that is never built". A matcher
  is exactly the thing that would justify building it.
- **CONFLICT-021 must be settled first** or the matched pair cannot get a
  conversation.

`FEATURE_STATUS.language_exchange` is `'coming'` and the feature is Phase 3, so
nothing is broken today by leaving it. What would be broken is repairing the
function into the middle of this.

- **Type:** FL-010 / PHANTOM_SCHEMA

**The dead names are consistent**: `video_sessions` and `session_participants`,

functions written against one imagined schema.

`information_schema.columns`, not just `information_schema.tables`.
`match-exchange-partner` passed the table check and failed the column check —
it was on the "clean, deployable" list until the columns were checked.

### CONFLICT-045: §64 renamed the tier values but not the column DEFAULTS, and two of the defaults are values their own CHECK rejects
- **Detected by:** tauka-flutter (backlog cleanup pass, plan O-12)
- **Date:** 2026-08-28
- **Type:** PARTIAL_RENAME / LIVE_OUTAGE
- **Status:** **RESOLVED 2026-08-28** — §81.1 and §81.2.

**What §64 did and did not do.** It renamed the tier values to
`free_tier | learner_tier | tutor_tier | intensive_tier`, rewrote every CHECK
constraint, and rewrote every stored value. It did not rewrite the column
DEFAULTS. Three survived with the old spelling:

| Column | DEFAULT was | Its CHECK | Effect |
|---|---|---|---|
| `app.user_profiles.subscription_tier` | `'free'` | `*_tier` OR NULL | **every INSERT omitting it failed** |
| `app.student.tier` | `'free'` | `*_tier`, no NULL escape | **every INSERT omitting it failed** |
| `app.gift_subscriptions.tier` | `'tutor'` | **none at all** | wrote a dead, role-ambiguous value |

**Verified, not inferred.** Rollback-safe probes against production:

```
ERROR: new row for relation "user_profiles" violates check constraint
       "user_profiles_subscription_tier_check"
ERROR: new row for relation "student" violates check constraint
       "student_tier_check"
```

**Consequence: no new account could complete onboarding.**
`_ensureUserProfile` (`supabaseService.dart:3619`) inserts
`{id, user_type, first_name}`; `upsertStudent` (`:3703`) inserts `{id}`. Neither
names a tier, and no trigger on `auth.users` creates a profile — those two are
the only creation path, since the web `/signup` creates nothing (O-14). Both call
sites catch the exception and return `false`, so it failed **silently**.

**This is CONFLICT-036's stated hazard, arriving.** `CLAUDE.md` carries it
verbatim: *"a partial rename recreates it, so tier values change in the database
and all three projects together or not at all."* The code half of §64 was
complete — no bare tier string survives in any of the three projects. Only the
defaults were missed.

**Why four audits missed it.** §71.3 reconciled `db.sql` against production by
comparing **column lists**, and found two real divergences in this very table
(`created_at`, `role` — plan O-12). CONFLICT-036 checked **stored values**, and
found the `min_tier = 'tutor'` rows. A DEFAULT is neither a column nor a value
nor a constraint, so both methods could be executed correctly and completely and
still leave a table that rejects every insert.

**The `gift_subscriptions` case is the instructive one.** Its default was the
bare `'tutor'` — the exact string `CLAUDE.md` forbids comparing a tier against,
because it collides with the tutor *role* — and it had no CHECK at all, so
nothing would ever have rejected it. It stayed latent only because
`gift_service.py:71` writes `'tutor_tier'` explicitly on the single insert path.
It also had a doc telling the next writer to do the wrong thing:
`test_referral.md:233` read *"uses canonical 'tutor' not 'tutor_tier'"*, true
before §64 and an instruction to write a banned value after it. Fixed.

**Method to carry forward:** after a value rename, check DEFAULTs as a separate
pass. `SELECT table_name, column_name, column_default FROM
information_schema.columns WHERE table_schema='app' AND column_default ~ '<old
value>'` is the whole check, and it takes one query.

### CONFLICT-044: the API and the database disagree about who is an admin — and about who is a tutor — and the API's answer to both is "nobody"
- **Detected by:** tauka-flutter (backlog audit)
- **Date:** 2026-08-28
- **Type:** AUTHZ_MISMATCH
- **Status:** **RESOLVED 2026-08-28** — both gates repointed at the tables the
  RLS policies already use. See *Resolution* at the end of this entry.

> **Widened on fix.** The entry as first written named `require_admin` only.
> `require_tutor`, ten lines above it in the same file, had the **identical**
> defect and took 20 tutor-facing endpoints down with it. It is recorded below
> rather than as a separate conflict because it is not a separate conflict — it
> is the same one, and the original audit stopped at the first instance.

**Two definitions of "admin", in two projects, and they were never reconciled.**

| Layer | Predicate | Answers today |
|---|---|---|
| tauka-python `require_admin` | `app_metadata.role == 'admin'` | **nobody** — 0 of 6 users carry the key |
| Postgres `app.is_admin()` | `app.admin_users WHERE id = auth.uid() AND deleted_at IS NULL` | **1 user**, a real one |
| tauka-python `require_tutor` | `app_metadata.role == 'tutor'` | **nobody** — same empty key |
| Postgres `app.is_tutor()` | `app.tutor WHERE id = auth.uid()` | **1 user**, a real one |

Every user's `raw_app_meta_data` is `{"provider": "email", "providers":
["email"]}`. No `role` key has ever been set on any account.

**Consequence.** All 22 `require_admin`-gated FastAPI endpoints return 403 to
every caller, including the actual admin: payout compute/approve/disburse, float
read and append, `student_tutor_link` assignment and evaluation, unmarked-session
review, all four handoff routes, both feedback-triage routes, commitment
cancellation and lookup, trust warnings, question-bank loading, and testimonial
approve/publish.

**This is not the CONFLICT-033 shape** (two definitions of "my student" that both
returned rows and disagreed at the edges). Here one definition returns rows and
the other returns nothing at all — so it does not fail at the edges, it fails
completely, for everyone, in one direction only.

**Why it went unnoticed for four sessions.** Nothing exercises it — though not
for the reason first recorded here. This entry originally said the admin routes
were "unit-tested with the dependency overridden". They are not: there is no
`dependency_overrides` anywhere in `tests/`, and no test issues a request to an
admin route at all. `test_payouts`, `test_handoff` and `test_standing` call
`payout_service`, `handoff_service` and `standing_service` **directly**. The gate
is not stubbed out; it is simply never reached. That is a worse position than the
one described, because a stub at least records that a gate exists.

There is also no admin UI (O-26), so no human has called these endpoints. And
O-08 recorded the situation as a *pending decision* with a recommendation, which
reads as "works, spelling undecided".

Same shape as **CONFLICT-041** one session earlier: an authz rule that survived
because nothing read it. **A gate with no traffic is unobserved, not verified.**

**One correction to O-08's wording, which matters.** The register says
`user_metadata.role`. The code reads **`app_metadata`**. `user_metadata` is
client-writable — a role check against it would let any user promote themselves
to admin. `app_metadata` is service-role-only. The implementation is *safer* than
the register describes; it is just empty. Anyone "fixing" this by writing the
role into `user_metadata` would open exactly the hole the current code avoids.

**Fix:** replace the metadata lookup in `app/dependencies.py:require_admin` with
a read of `app.admin_users` (service role, `deleted_at IS NULL`), matching
`app.is_admin()`. No migration; the table exists and is populated. Phase 0e's
"decision" was already answered by the 40-odd RLS policies that depend on it.

---

**Resolution — 2026-08-28.**

`app/dependencies.py` now reads the tables, not the metadata:

| Gate | Reads | Matching policy function |
|---|---|---|
| `require_admin` | `app.admin_users` where `id = <sub>` and `deleted_at IS NULL` | `app.is_admin()` |
| `require_tutor` | `app.tutor` where `id = <sub>` and `deleted_at IS NULL` | `app.is_tutor()` |

Three things about the shape of the fix, because each was a choice:

- **Both gates fail closed.** An exception reading the table produces 403, never
  a grant. An unreachable database is not a permission.
- **`deleted_at IS NULL` is applied to `app.tutor` even though `app.is_tutor()`
  omits it.** That is a deliberate one-directional divergence: the API is
  *stricter* than the policies, so a soft-deleted tutor is refused by the
  endpoint and would have been admitted by RLS. The reverse would be the bug.
  **`app.is_tutor()` not filtering `deleted_at` is a live latent issue in its own
  right** — it is not fixed here because changing a SECURITY DEFINER function
  every tutor RLS policy depends on is not a side effect of an API fix.
- **`app.tutor.status` is deliberately not checked.** A suspended tutor must
  still be able to read their own standing and payout settings; suspension is not
  an account lock.

**Regression cover:** `tauka_py_backend/tests/test_role_gates.py`, 8 tests,
through `TestClient` on purpose — a gate is only tested where a request meets it.
One of them asserts that neither gate calls `auth.admin.get_user_by_id`, so the
metadata shape cannot quietly return.

### CONFLICT-042: `app.anki_deck_assignment`'s INSERT policy constrains the assigner and not the assignee
- **Detected by:** tauka-flutter (implementation plan Phase 6, §13.3)
- **Date:** 2026-08-28
- **Type:** RLS_SCOPE
- **Status:** **RESOLVED 2026-08-28** (§81.4, plan O-28). The policy now reads:

  ```sql
  WITH CHECK (
    assigned_by = auth.uid()
    AND assigned_to_user_id IS NOT NULL
    AND app.teaches_student(assigned_to_user_id)
    AND assigned_to_class_id IS NULL
  )
  ```

  `assigned_to_class_id` is required NULL: `teaches_student()` answers a question
  about one student and cannot express class-level authority, so leaving the
  class id unconstrained would have preserved a smaller hole of exactly the shape
  being closed. Class assignment is therefore closed to tutors until a
  class-level predicate exists — a deliberate narrowing, chosen over a partial
  fix. Admins are unaffected: `admins manage all deck assignments` is a separate
  permissive FOR ALL policy and is OR'd with this one.

  **Found by declining to copy it.** §79 wrote `exercise_assignment` to the same
  shape and deliberately did not reuse this policy; that refusal is what
  surfaced the hole. Worth repeating as a method.

**The policy.**

```sql
CREATE POLICY "tutors insert deck assignments"
  ON app.anki_deck_assignment FOR INSERT
  WITH CHECK (assigned_by = auth.uid());
```

`assigned_to_user_id` is unconstrained and there is no `app.is_tutor()` branch
despite the policy's name, so **any authenticated user can assign a deck to any
other user**. The check only stops you lying about who you are.

**Found while writing `app.exercise_assignment`**, which plan §13.3 says to model
on this table: *"`app.anki_deck_assignment` is already 'a tutor assigns study
material to a student'. Mirror its shape rather than inventing a second
pattern."* The **shape** was mirrored; the policy deliberately was not.
`exercise_assignment_insert_tutor` requires
`tutor_id = auth.uid() AND app.teaches_student(student_id)`.

**Impact today:** low. 0 rows, and the worst outcome is an unexpected deck in
someone's list. Logged rather than fixed because changing it is a change to a
shipped feature's write path and belongs in its own change, with the Flutter
caller checked first.

**Recommended fix:** `WITH CHECK (assigned_by = auth.uid() AND
app.teaches_student(assigned_to_user_id))`, plus a decision about
`assigned_to_class_id`, which `teaches_student` cannot express.

### CONFLICT-041: `app.voice_recordings` let every tutor read every student's recordings
- **Detected by:** tauka-flutter (implementation plan Phase 6, §13.1)
- **Date:** 2026-08-28
- **Type:** RLS_SCOPE
- **Status:** **RESOLVED** in §79, same day, with developer authorisation.

**The policy, as it stood in production:**

```sql
voice_recordings_select_own_or_tutor_admin
  USING (user_id = auth.uid() OR app.is_tutor() OR app.is_admin())
```

**`app.is_tutor()` takes no argument.** It answers *"is the caller a tutor"*, not
*"is this their student"*. So the middle branch is not a scope at all: any tutor
could read any student's voice recordings, including students they had never
taught and students on courses they had nothing to do with.

**This is not the CONFLICT-033 shape.** That was two definitions of "my student"
disagreeing — five policies, four using the course join and two (not one — the
entry undercounted) using `student.tutor_id`. This is a policy with **no**
definition of "my student" in it, in the heaviest data category the platform
holds (`legal.md` L-006: a voice recording is a third category, and the L-001
enrolment argument "does not obviously stretch to cover it").

**The sibling table gets it right.** `speech_submission_tutor_read` uses
`app.can_read_activity(user_id)` — the course join AND a paid tier. Both tables
hold voice; they now carry the same rule:

```sql
voice_recordings_select_own_or_teacher_admin
  USING (app.can_read_activity(user_id) OR app.is_admin())
```

Strictly narrower in every direction. Safe to apply: the table holds **0 rows**,
so nothing was revoked from anyone who had data.

**How it was found:** by reading the policy while scoping the tutor-mediated
then-vs-now feature (§13.1), which is the first thing that has ever read this
table. It had been live and unexercised, which is exactly the condition under
which a too-wide policy attracts no attention.

**The generalisation, now an anti-pattern in `ARCHITECTURE_INDEX.md`:** a
row-level read rule whose only non-admin branch is a **subjectless** predicate
is not scoped. `app.is_admin()` and `app.is_tutor()` are role checks; the
subject-taking predicates are `app.teaches_student(uuid)` and
`app.can_read_activity(uuid)`. Picking the role check by mistake produces a

| | `app.test_referrals` | `app.tutor_referral_link` + `app.referral_signup` |
|---|---|---|
| Domain | `test_referral` | `tutor_management` |

- merge the two table sets, or add a UNIQUE to `test_referrals.sender_student_id`

### CONFLICT-035: `cohort_assignments` RLS compares a column to itself, so any cohort member can read every cohort's assignments
- **Detected by:** tauka-flutter (tutor-cohort plan, §5.0 ownership check)
- **Date:** 2026-08-24
- **Status:** OPEN — **fix before the first cohort_assignments row is written**
- **Type:** RLS_DEFECT (security)
- **Details:** `cohort_assignments_select_member_or_tutor_admin` reads:

  ```sql
  app.is_tutor() OR app.is_admin() OR EXISTS (
    SELECT 1 FROM app.cohort_memberships cm
     WHERE cm.cohort_id = cm.cohort_id      -- ← compares the column to itself
       AND cm.user_id   = auth.uid())
  ```

  `cm.cohort_id = cm.cohort_id` is a tautology. The correlation to the outer row
  — `cm.cohort_id = cohort_assignments.cohort_id` — was never written, so the
  membership branch collapses to **"is the caller a member of any cohort at
  all"**. Any student in any cohort can therefore read **every** cohort's
  assignments platform-wide: which decks and content were assigned to which
  group, and by whom.

  The alias makes it invisible on a quick read — `cm.cohort_id = cm.cohort_id`
  looks like a join condition and is shaped like one.

  **Nothing has leaked: the table holds 0 rows** and no cohort has ever formed.
  This is a pre-launch find, which is the only good time to find it.

  Also noted while here, not a defect but worth a decision: `cohorts_select_all_auth`
  is `USING (true)` — every authenticated user reads every cohort row. Defensible
  for `(name, description, tutor_id, dates)`; less so once the tutor-cohort plan
  adds level, weekly slot and timezone, which turns it into a browsable directory
  of who teaches what and when. Same concern that made `user_profiles` "not a user
  directory".
- **Fix:**

  ```sql
  CREATE POLICY cohort_assignments_select_member_or_tutor_admin
    ON app.cohort_assignments FOR SELECT USING (
      app.is_tutor() OR app.is_admin() OR EXISTS (
        SELECT 1 FROM app.cohort_memberships cm
         WHERE cm.cohort_id = cohort_assignments.cohort_id
           AND cm.user_id   = auth.uid()));
  ```

  **Land it on its own, not inside a feature migration.** A security fix buried in
  a schema change is a security fix nobody reviews.
- **Lesson worth keeping:** this is the third defect in this codebase that no test
  and no analyser could see — after the table names in string literals (FL-010)
  and the doc claims that outlived their code. **RLS predicates are code that only
  the database executes**, and the only way to check one is to read it or probe it
  with a real JWT. The activity domain's policies were probed that way in phase 12
  and were correct; these never were.

| `activity_summary.app_streak` / `learn_streak` | the client, in `ActivityUploader.publishSummary()` | The genuinely derived pair — and **nothing reads them** |

So the derived streaks exist and are unread; the read streak is undermined; and
the second read streak is dead. `achievementService` reads `streak_days`, i.e.
the counter, which is what it always read.

**The `streak-reset` cron is not the problem.** It is still scheduled
(`0 3 * * *`, zeroing `streak_days` where `last_active_date < CURRENT_DATE - 1`)
and it is *coherent* with `update_user_streak` — both key on `last_active_date`,
which the RPC maintains. The pair works as it always did. It is only the
documentation that moved.

**Why this is not a silent fix.** Which streak wins is a product decision with
two defensible answers:

1. **Point the readers at the derived pair.** Consistent with the plan's own rule
   that counts are derived and never incremented. Costs: `publishSummary()` also
   writes `user_profiles`, the RPC and the cron are retired, and
   `achievementService` keeps reading the same column with a new meaning.
2. **Keep the counter and delete `learn_streak_days`.** The counter works, is
   shipped, and nothing has complained. Costs: the plan's "derived, never
   incremented" invariant does not hold for the streak a user actually sees, and
   that should be written down rather than left implied.

### Resolution (2026-08-23) — option 1

`ActivityUploader.publishSummary()` now writes **both** `streak_days` and
`learn_streak_days` onto the caller's own `user_profiles` row, from the same
derived pair the summary carries. Every existing reader — `achievementService`,
the `idx_user_profiles_streak` leaderboard index, whatever the tutor dashboard
becomes — gets the derived value with no change at the call site, and
`learn_streak_days` comes alive.

Retired in the same change, because a counter and a derived value writing one
column fight and the counter is the half that cannot be audited:

| Retired | Where |
|---|---|
| `SupabaseService.updateStreak()` call | `mainProgressManager.dart:704` — removed |
| `SupabaseService.updateStreak()` method | removed, with a do-not-reinstate note |
| `app.update_user_streak(uuid)` | **dropped** — migration `streaks_derived_not_incremented` |
| `streak-reset` cron | **unscheduled** — same migration |

**The cron is the dangerous half, and the ordering matters.** With the RPC gone
nothing maintains `last_active_date`, so it goes stale for every active user —
and the cron would then zero a **correct** derived streak every night at 03:00
UTC. It was not firing at the time only because every `last_active_date` was NULL and
`NULL < CURRENT_DATE - 1` is NULL, so no row matched — luck, not design. **Applied
2026-08-23**, and verified after: the cron is gone (1 → 0), the RPC is gone, no
cron mentions streaks, and `add_user_xp` / `weekly-xp-reset` survive untouched
because XP genuinely is an accumulator.

The client's new write path was **probed as `authenticated`** rather than
inferred from `user_profiles_update_own` and the privilege-guard trigger:

| Probe | Result |
|---|---|
| client updates **its own** `streak_days` + `learn_streak_days` | changed 1 row; values persisted |
| client updates **another user's** `streak_days` | changed **0** rows |

Probe values reset to zero afterwards.

Checked before dropping: **no other database object calls `update_user_streak`**
(0 functions, 0 triggers), and `streak-reset` is the only cron mentioning
streaks.

`last_active_date` is now legacy and nothing writes it; the live answer is
`app.activity_summary.last_active_on`.

- **The invariant this restores:** every count in this system is derived from
  events and none is incremented. It now holds for the streak a user actually
  sees, which was the one place it did not.
- **Related:** CONFLICT-005 (the two pre-existing streak columns, resolved
  by design) and CONFLICT-031 (the same column's documentation naming a dropped
  function — that entry corrected the *writer*; this one is the larger finding
  behind it).

### CONFLICT-030: SCHEMA_REQUEST — `app.ai_usage` sits in tauka-flutter's domain and only tauka-python can write it
- **Detected by:** tauka-flutter (phase 9 of `activity-telemetry-plan.md`)
- **Date:** 2026-08-23
- **Type:** SCHEMA_REQUEST + CROSS_PROJECT_WRITE
- **Status:** RESOLVED 2026-08-23 — decided, built, applied and probed. The arrangement below stands as the thing to keep honouring.

**The problem, as §10 of the plan framed it.** The `ai` domain is tauka-flutter's.
But the number this table exists to hold — what the model actually charged — is
only ever seen by tauka-python, which is the only project that talks to a
provider. Neither "tauka-flutter owns it" nor "tauka-python owns it" is right on
its own.

- **Resolution taken:** the `app.student.tier` pattern. **tauka-flutter owns the
  DDL** (it is the `ai` domain, documented in `tauka/shared-db/domains/ai.md`);
  **tauka-python is the sole writer**, via service role. Chosen over inventing a
  second arrangement for a problem that already has a documented, working one.
- **This project assumes:** tauka-python's write on `app.ai_usage` is **INSERT
  only**. No UPDATE, no DELETE, no DDL, no reads. If tauka-python is ever seen
  doing anything else with this table, that is a bug and not a change of policy.
- **The RLS differs from `activity_event` on purpose.** There, the client was the
  producer and had an INSERT policy. Here the client is the *subject*, so it gets
  SELECT on its own rows and **no INSERT policy at all** — a spend ledger a client
  can write is a ledger that reports whatever the client likes. No UPDATE or
  DELETE policy exists for anyone.
- **Do not reconcile it against Redis.** Redis holds a pre-flight estimate
  (`count_tokens(prompt) + 500`), expiring and failing open; this holds a
  post-hoc measurement, kept. They are supposed to differ. A future maintainer
  finding the two disagreeing has found the design, not a bug.
- **Applied 2026-08-23** as migration `ai_usage_ledger`, and the RLS **probed as
  `authenticated` with the JWT claim set**, rather than inferred from the absence
  of a policy:

  | Probe | Result |
  |---|---|
  | service role INSERT (as tauka-python) | allowed |
  | **student INSERTs a usage row for themselves** | **DENIED** |
  | student SELECTs own rows | visible |
  | student SELECTs another user's rows | invisible |
  | student UPDATE | ran, changed **0** rows |
  | student DELETE | ran, removed **0** rows |
  | `source` = anything but provider/estimate | rejected by CHECK |
  | negative `total_tokens` | rejected by CHECK |

  The student-INSERT denial is the one that matters: it is the difference between
  a ledger and a self-reported figure. Probe rows deleted; the table is back to
  zero.

### CONFLICT-029: the `activity` bucket never cascaded on account deletion, and tauka-python now deletes rows in a table it does not own
- **Detected by:** tauka-flutter (building phase 12 of `activity-telemetry-plan.md`)
- **Date:** 2026-08-23
- **Type:** PRIVACY_GAP + CROSS_PROJECT_WRITE
- **Status:** RESOLVED 2026-08-23 — migration `activity_retention_helpers` applied and probed; the nightly sweep now removes a deleted account's files. The cross-project write arrangement in (c) stands as documented and is the part to keep honouring.

**Two things, logged together because the fix is one job.**

**(a) Account deletion did not delete the activity files.** Verified against the
live database rather than assumed:

| | Cascades from `user_profiles`? |
|---|---|
| `app.activity_file` | yes — `activity_file_user_id_fkey`, `ON DELETE CASCADE` |
| `app.activity_summary` | yes — `ON DELETE CASCADE` |
| the `activity` **bucket** | **no. There is no foreign key and there never was.** |

So deleting an account removed the catalogue and left the per-device JSONL sitting
in Storage — unreferenced, unreachable through the app, and still a
minute-by-minute record of what a person did. `activity-telemetry-plan.md` §11
and `tauka/shared-db/domains/activity.md` both stated that deletion actually
deletes. **That sentence was false for anything already uploaded**, from the day
the bucket was created (2026-08-23, session 27) until phase 12.

Nothing was leaked: the bucket is private, and no account has been deleted since
it existed — `activity_file`, `activity_summary` and the bucket were all empty
at the time of writing. The gap was structural, not exploited.

**(b) Deleting a row from `storage.objects` in SQL does not delete the file.** It
removes the metadata and orphans the blob. Only the Storage API removes bytes.
This is why the sweep cannot be pg_cron and has to be a service that makes HTTP
calls — which is tauka-python, and which is what creates (c).

**(c) tauka-python now DELETEs from `app.activity_file`, which tauka-flutter
owns.** `shared-db/OWNERS.md` said "tauka-flutter only". The alternative was to
put deletion in the client, which cannot work: the device whose files have
expired is very often the device that never comes back.

- **This project assumes:** tauka-python's write on `app.activity_file` is
  **DELETE only**, and only for rows whose `covers_to` is already past the
  retention window. No INSERT, no UPDATE, no DDL — the `app.student.tier`
  precedent, narrowed further. If tauka-python is ever seen writing this table
  any other way, that is a bug and not a change of policy.
- **Resolution taken:** `OWNERS.md` marks `activity_file` SHARED-WRITE (narrow)
  and names the exact permitted operation. Two `SECURITY INVOKER` helper
  functions granted to `service_role` only —
  `app.expired_activity_files()` and `app.orphaned_activity_objects()` — keep the
  path selection in SQL, where it is cheap, without giving any client a new way
  to enumerate anything.
- **Applied 2026-08-23** as migration `activity_retention_helpers`, and probed
  against seeded rows rather than assumed:

  | `covers_to` age | Result |
  |---|---|
  | 300 days | expired -> deleted |
  | **91 days** | expired -> deleted |
  | **90 days (the cutoff itself)** | **kept** |
  | 2 days, `covers_from` 120 days (straddles) | **kept** — the owning device's to shed |
  | 0 days | kept |

  The SQL boundary agrees with the Dart one (`isBefore(cutoff)`), which is the
  cross-check that matters: two implementations of one rule, and an off-by-one in
  either silently deletes a day of someone's history. `anon` and `authenticated`
  hold **no** EXECUTE on either function; `service_role` holds both. Probe rows
  deleted afterwards — `activity_file`, `activity_summary` and the bucket are
  back to zero.

### CONFLICT-014: app.user_profiles UPDATE policy recurses (42P17) — every owner write fails
- **Detected by:** tauka-flutter
- **Date:** 2026-08-19
- **Type:** BROKEN_POLICY
- **Status:** RESOLVED 2026-08-19 — §58 applied to production (migration `fix_user_profiles_policy_recursion`). Verified: the recursive policy is gone and `trg_guard_user_profile_privileges` is in place.
- **Details:** The §48 policy `"users update own profile"` enforces the no-self-promotion
  rule with a `WITH CHECK` that selects from `app.user_profiles` — the table it guards:
  ```sql
  WITH CHECK (
    user_type = (SELECT user_type FROM app.user_profiles WHERE id = auth.uid())
    AND subscription_tier = (SELECT subscription_tier FROM app.user_profiles WHERE id = auth.uid())
  )
  ```
  Evaluating it re-enters the policy, so **every** owner UPDATE fails with
  `infinite recursion detected in policy for relation "user_profiles" (42P17)`.
  `app.is_admin()` and `app.shares_conversation_with()` are both SECURITY DEFINER and are
  NOT implicated.
- **Blast radius:** onboarding never persists. Production shows `user_type` and
  `completed_at` null for 3 of 5 `auth.users`. Because `AuthStateManager` resolves the
  app-wide role from `user_profiles.user_type`, every tutor reads back as a student, and
  a user who completes onboarding is walked through it again on the next device.
- **Resolution (§58):** a policy cannot see `OLD`, which is why the original reached for
  a subquery. Move the rule to a `BEFORE UPDATE` trigger, which can, and drop the policy.
  The trigger clamps the two protected columns rather than raising, so a self-promotion
  attempt is a no-op on those columns while the legitimate part of the write still lands.
  It exempts `auth.uid() IS NULL` (service role, and `trg_sync_student_tier` writing
  `subscription_tier` from `app.student.tier`) and admins, and permits `user_type`
  NULL → value once, which is onboarding choosing a role.
- **Apply:** run §58, then re-open the app; `OnboardingData._flushPendingRemote` rewrites
  the missing fields on next launch.

### CONFLICT-018: the `user_profiles` self-promotion guard is inert — two permissive UPDATE policies OR together
- **Detected by:** tauka-flutter
- **Date:** 2026-08-12
- **Type:** RLS_BYPASS (security)
- **Status:** OPEN — **needs a human decision before any policy change**
- **Details:** `app.user_profiles` carries **two** permissive UPDATE policies for the
  `authenticated` role:

  | Policy | USING | WITH CHECK |
  |---|---|---|
  | `users update own profile` | `auth.uid() = id` | `user_type` unchanged **AND** `subscription_tier` unchanged |
  | `user_profiles_update_own` | `auth.uid() = id AND deleted_at IS NULL` | `auth.uid() = id` |

  PostgreSQL combines permissive policies for the same command with **OR**. The second
  policy's `WITH CHECK (auth.uid() = id)` is true for a user's own row, so the whole check
  passes regardless of what the first policy says. The guard it was written to provide —
  §48, "the Flutter client never modifies `user_type` directly" — does not hold.

  Consequence: any authenticated user can `UPDATE app.user_profiles SET subscription_tier
  = 'intensive', user_type = 'tutor' WHERE id = auth.uid()`. `TierGatingService` reads
  `user_profiles.subscription_tier` for feature gating, so this is a client-side paid-tier
  bypass, and `user_type` drives which UI (student vs tutor) is rendered.

  Verified against production on 2026-08-12 by reading `pg_policies`, not inferred from docs.
- **Contradicts the docs:** `tauka/shared-db/domains/identity_access.md` §2 "Key invariants"
  states `user_type` is "never modified by the Flutter client directly (§48 RLS policy
  blocks self-promotion)" and that `role` may only be written by service_role. Neither is
  currently true; there is also **no `role` column** on the table in production.
- **Why it is not fixed here:** tightening this changes authentication behaviour for every
  existing client. Note that the Flutter onboarding write *relies* on the permissive
  outcome today — `OnboardingData._toMap()` sends `user_type` on every step, and tightening
  the policy without changing that code would break onboarding for every new sign-up.
  The two must move together.
- **Suggested resolution (needs approval):** drop `user_profiles_update_own`, keep the
  guarded policy, and add `deleted_at IS NULL` to its `USING`. Then either stop sending
  `user_type` from `_toMap()` after the first write, or add a narrow policy permitting
  `user_type` to be set exactly once while it is NULL.

### CONFLICT-027: `upsert_unit_progress()` reset `completed_at` on every call, and trusted its caller's `p_user_id`

- **Details:** Two defects in a function that had never been called, found while
  writing its first caller.

  1. **`completed_at` moved forward on every sync.**
     ```sql
     completed_at = CASE WHEN EXCLUDED.status = 'completed' THEN now() ELSE ... END
     ```
     Any re-upsert of a completed unit stamped it with the moment of the sync.
     The pace graph steps at that date and must be monotonic; left alone, every
     reconnect would have walked the graph forward and overwritten the client's
     correct local date. `started_at` had the milder version:

     it — the same reason CONFLICT-026 went unnoticed.

**Why it matters beyond tidiness.** `dtw-speech-drills-plan.md` §7.3 planned to
ship a whole feature behind a `feature_flag` row *on the strength of this
documentation*, describing it as "already read by the Flutter client on startup".
That plan's phase 6 gate assumes the feature can be switched off without a
release if the calibration distributions disappoint. **There is no switch.** The
plan has been corrected and now carries this as its §14.5 open decision.

**Also worth noting before anyone builds the reader:** `notify_me_count` on that
table suggests it was designed for the web site's "coming soon / notify me" flow
rather than as a runtime kill switch. Reusing it as one may be the wrong call
even once a reader exists.

**Resolved:** the reader was built —
`tauka/lib/src/services/speech/feature_flags.dart`, the first and only thing in
this project that queries the table. `OWNERS.md:183` corrected: the columns are
`key`/`status`, not `name`/`enabled`, and `TierGatingService` does not read it.

Two decisions worth carrying forward:

* **It fails open.** A network error, a missing row, an unreadable response all
  mean *not disabled*. The flag exists to turn something off deliberately, and
  one that silently disabled a feature whenever Supabase hiccupped would take
  speaking drills down for offline learners — most of them, in a product whose
  premise is working offline.
* **It is read once per session**, not per render. A kill switch is an
  operational decision, not a per-frame check, and a network call inside the
  §10.3 latency budget would be a bug.

The `notify_me_count` column still shows this table was built for the web site's
"coming soon" flow. Reusing it as a runtime switch is a slight stretch and was
the cheapest correct option; if flags become load-bearing, they deserve their
own table rather than sharing one with a marketing counter.
